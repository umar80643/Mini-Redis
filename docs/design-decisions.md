# Design Decisions

- **asyncio:** many mostly-I/O-bound clients without a thread per socket.
- **RESP over TCP:** compatible with `redis-cli` for the implemented command subset and demonstrates stream framing.
- **Binary-safe bytes:** keys/values remain bytes through protocol and storage.
- **Versioned TTL heap:** O(log n) scheduling without scanning the keyspace; stale heap records cannot delete renewed keys. Verified directly in `tests/unit/test_ttl_heap_versioning.py`.
- **Execution gate + storage lock:** normal commands may proceed concurrently while short storage critical sections make individual operations atomic. EXEC takes an exclusive gate window so its queued commands cannot be interleaved. This avoids serializing every client command behind one global command lock. Verified in `tests/unit/test_transactions.py`.
- **Approximate LRU/LFU:** exact metadata-based choices are easy to explain; they intentionally differ from Redis's optimized sampled implementations.
- **RESP AOF:** human-inspectable/replayable and reuses the protocol parser.
- **Snapshot + AOF rotation:** avoids replaying pre-snapshot mutations and TTL extension on normal snapshot boundaries.
- **AOF rewrite/compaction:** long-running servers accumulate an AOF far larger than the actual dataset; `BGREWRITEAOF` collapses history down to the minimal reconstructing commands, swapped in via the same temp-file-plus-atomic-rename pattern as snapshots so a crash mid-rewrite can't corrupt the log. Verified in `tests/persistence/test_aof_rewrite.py` and `tests/persistence/test_bgrewriteaof_recovery.py` (the latter actually restarts a server against a rewritten file).
- **Bounded Pub/Sub queues:** protects memory and publisher latency; messages can be dropped for persistently slow subscribers.
- **Replication reuses the Pub/Sub delivery pattern:** a primary pushes writes to each attached replica via the same bounded-queue-plus-dedicated-pusher-task shape already used for Pub/Sub — one mental model for "stream events to a connection without blocking on it," applied twice.
- **Full resync via the existing JSON snapshot code, not a separate format:** `PSYNC`'s full-resync payload is exactly `persistence.snapshot_bytes()` — the same function that backs disk snapshots — sent over the wire instead of written to a file. One well-tested serialization path, two consumers.
- **Partial resync via a bounded in-memory backlog, not a WAL:** the primary keeps a capped buffer of recently-propagated command bytes; a reconnecting replica whose last offset is still covered by that backlog gets just the missing commands instead of a full snapshot. Simpler than a persistent replication log, at the cost of only covering "recent" gaps — a replica down longer than the backlog window falls back to full resync, which is still correct, just more expensive.
- **Asynchronous, not synchronous, replication:** the primary never blocks a client's write on a replica's acknowledgment. Simpler and lower-latency, at the explicit cost of a promoted replica potentially missing the last few unacknowledged writes after a primary failure — see `docs/interview-guide.md` question 29 for the CAP framing.
- **Fixed-delay reconnect, not exponential backoff:** a replica that loses its primary link retries after a constant delay. Deliberately simpler than a production backoff-with-jitter policy, in service of staying whiteboard-explainable — noted as a place a production system would do more.
- **Read-only replicas enforced at the command-dispatch layer, not the storage layer:** `MiniRedisServer.execute` rejects writes from ordinary client connections when `role == "replica"`, before the command ever reaches `Storage`. Writes arriving over the replica's own master link are exempt (they're internally dispatched with no client connection object), so the enforcement point is "did a real client ask for this," not "is this a mutating command."
