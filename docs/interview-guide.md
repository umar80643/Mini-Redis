# Interview Guide

Answers below describe what MiniRedis actually does, not generic Redis trivia — if a question has a real implementation detail, the answer names it and points at the file.

## Why this project

1. **Why build MiniRedis at all?** To demonstrate the systems-engineering judgment a backend interview actually probes — correct concurrency over shared mutable state, durability trade-offs, TTL scheduling that doesn't leak memory, backpressure that doesn't cascade, and (now) real primary-replica replication — with working, tested code rather than a description of how Redis works.
2. **Why asyncio instead of threads or multiprocessing?** The workload is I/O-bound: most of the time, a connection is idle waiting for the next command. `asyncio` handles many concurrent idle sockets on one thread without the memory/context-switch cost of a thread per client, and it makes "which operations can interleave" an explicit design decision (via locks/gates) instead of something the GIL happens to paper over.

## Networking and protocol

3. **Why can't you trust TCP message boundaries?** TCP is a byte stream, not a message stream — it guarantees ordered, reliable delivery of bytes, nothing about how those bytes get grouped into `read()` calls. A client's single RESP command can arrive split across two reads, or ten pipelined commands can arrive in one read. See `server/tcp_server.py::_drain_commands`.
4. **How does the incremental RESP parser handle that?** `protocol/core.py::parse_one` is fed a growing buffer and either returns `(value, bytes_consumed)` or raises `NeedMoreData`. The caller keeps whatever's left in `buf` after each successful parse and appends new bytes as they arrive — it never assumes a read boundary lines up with a command boundary.
5. **What does RESP framing actually look like?** A type prefix byte (`+` simple string, `-` error, `:` integer, `$` bulk string, `*` array) followed by CRLF-terminated content; bulk strings and arrays declare their length up front so the parser knows exactly how many bytes/elements to consume.
6. **What backpressure mechanisms exist?** Bounded request size and array length (reject oversized frames outright), a connection limit, an idle timeout, `await writer.drain()` before accepting more work on a connection, and bounded per-connection queues for both Pub/Sub and replication delivery (drop rather than block a slow consumer).

## Storage and concurrency

7. **What's the storage engine's complexity?** O(1) average for GET/SET/DEL (dict-backed), O(log n) for scheduling a TTL (heap push), O(1) amortized for popping due TTLs, O(n) for `KEYS`/pattern scan (documented — use `SCAN` for large keyspaces).
8. **How do you guarantee no race condition on a shared key?** Every `Storage` method acquires a single `asyncio.Lock` for its full critical section (see `storage/engine.py`). Because Python's asyncio is cooperatively scheduled, holding that lock across an `await`-free critical section is enough to make `INCR`, `SET`, etc. atomic with respect to every other storage operation — verified directly in `tests/integration/test_concurrency_extra.py::test_concurrent_get_set_never_sees_a_torn_value`.
9. **Why a min-heap for TTLs instead of scanning the keyspace?** A heap gives O(log n) scheduling and O(1) access to "what expires next," versus O(n) to scan every key looking for expired ones.
10. **What happens to a heap record when a key's TTL changes or the key is overwritten?** Each heap record captures the entry's `version` at scheduling time. When popped, it's only honored if it still matches the key's *current* version — otherwise it's silently discarded. Without this, a shortened-then-extended TTL would leave a stale record that deletes a key that's supposed to live much longer. Proven directly in `tests/unit/test_ttl_heap_versioning.py`, not just asserted in a comment.
11. **Lazy vs. active expiration — why both?** Lazy (check-on-access) is free and immediate for keys that get read, but leaves memory unreclaimed for keys nobody reads again. Active expiration (a background sweep every 100ms) reclaims that memory and advances the `expired_keys` metric even for cold keys.
12. **LRU vs LFU trade-off?** LRU evicts by `last_accessed` — cheap, works well for recency-biased workloads, but can evict something about to be reused. LFU evicts by `access_count`, tie-broken by `last_accessed` (so an old-but-once-popular key doesn't block eviction forever) — better for skewed/stable access patterns, costs a counter update per access.
13. **How is memory accounted for eviction decisions?** Key + value byte length plus a fixed per-entry overhead estimate (`storage/memory.py`). Deliberately approximate — good enough for consistent *relative* eviction ordering, explicitly not claimed as exact process RSS.

## Transactions and Pub/Sub

14. **How is MULTI/EXEC isolated from other clients?** Queued commands don't execute until `EXEC`, which acquires the server's execution gate in *exclusive* mode (`server/lifecycle.py::ExecutionGate`) — it waits for any in-flight ordinary commands to finish, then blocks new ones from starting until the whole queued batch has run. Ordinary commands only need shared admission (they can run concurrently with each other); a transaction needs the stronger "nothing else touches state mid-batch" guarantee. Verified with 40 concurrent transactions racing a shared counter in `tests/unit/test_transactions.py`.
15. **Why not just wrap every command in one global lock instead of a separate gate?** That would serialize the entire server behind every single command, even though per-operation atomicity is already guaranteed by `Storage`'s own lock. The gate only pays the "stop the world" cost for the operation that actually needs it (EXEC).
16. **Why is `WATCH` not implemented?** It's called out explicitly as a limitation rather than silently missing — optimistic locking adds real complexity (tracking per-key touch versions across arbitrary command sequences) that wasn't worth the scope for this project's goals.
17. **How does Pub/Sub avoid a slow subscriber blocking everyone else?** Each connection has a bounded `asyncio.Queue`; `publish()` uses `put_nowait` and drops the message for that subscriber on `QueueFull` rather than blocking the publisher or other subscribers. Verified in `test_slow_pubsub_subscriber_does_not_block_publisher_or_other_subscribers`.

## Persistence

18. **How does the AOF work?** Every write command is RESP-encoded and appended to a file as it happens; replaying that file from an empty keyspace reconstructs exact history. TTLs are persisted as *absolute* (`PXAT`) timestamps, not relative ones, so replay after downtime doesn't reset the clock.
19. **What are the fsync trade-offs?** `always` fsyncs every write (zero data loss, lowest throughput), `everysec` batches fsyncs on a 1-second timer (up to ~1s of writes lost on crash, high throughput — the default), `no` never explicitly fsyncs and relies on the OS (fastest, weakest guarantee, can lose more than 1s of writes on a real crash vs. a clean process exit).
20. **What happens if the process crashes mid-write to the AOF?** The final RESP record may be truncated; `AOF.read_commands` stops cleanly at the first incomplete record it can't fully parse (`NeedMoreData`) and discards it, keeping everything before it. Corruption *inside* an otherwise-complete record is treated as fatal rather than silently skipped, since that could mean silently losing an unknown amount of history.
21. **What does AOF rewrite/compaction do, and why?** A long-running server's AOF holds the full mutation history, which can be far larger than the actual dataset (every `INCR`, every overwritten `SET` is still in the log). `BGREWRITEAOF` (`persistence/core.py::AOF.rewrite`) replaces that history with the minimal set of `SET` commands that reconstruct current state, then atomically swaps it in via temp-file-plus-`os.replace` — a crash mid-rewrite can never corrupt or lose the existing AOF, since the old file stays valid until the new one is fully written and renamed over it.
22. **What's the difference between a snapshot and the AOF?** A snapshot is a full point-in-time JSON dump of the keyspace — cheap to load (no replay), used together with an AOF reset (on `SAVE` or clean shutdown) to bound AOF growth. The AOF is the source of truth for anything written *since* the last snapshot.
23. **How does startup recovery work end to end?** Load the latest snapshot (if any) into an empty keyspace, then replay every AOF command written since — reconstructing exact state up to the moment of the last successful write, minus at most one truncated tail record from a crash.

## Replication

24. **How does primary-replica replication work here?** A replica connects to the primary and sends `REPLCONF listening-port <port>` then `PSYNC <replid> <offset>`. The primary replies either `+FULLRESYNC <replid> <offset>` followed by a JSON snapshot (if it can't serve from its backlog), or `+CONTINUE <replid>` followed by just the missed commands (if it can). After that handshake, the primary pushes every subsequent write command to the replica over the same connection — reusing the exact bounded-queue-plus-dedicated-pusher-task pattern already used for Pub/Sub delivery, so a slow replica can't block the primary.
25. **What is a replication offset, concretely?** A monotonically increasing byte counter (`master_repl_offset` on the primary, `replica_offset` on the replica) that advances by the encoded length of each propagated command. It's what lets a reconnecting replica tell the primary "I have everything up to byte N" and get exactly what it's missing.
26. **How is replica lag measured?** The primary tracks each attached replica's last-acknowledged offset (via periodic `REPLCONF ACK <offset>` from the replica); lag is `master_repl_offset - replica's_ack_offset`, reported per-replica in `INFO`'s `# Replication` section.
27. **What happens when a replica disconnects and reconnects?** The replica's read loop gets a `ConnectionError` (EOF or socket error), backs off for a fixed delay, and retries the full `REPLCONF`+`PSYNC` handshake from the top with its last-known offset. If the primary's backlog still covers that offset, it's a cheap partial resync; if too much time/data has passed, it falls back to a full resync. Verified end-to-end (forcibly severing the TCP connection from the primary side mid-test) in `tests/replication/test_replication.py::test_replica_reconnects_after_link_is_severed_and_catches_up`.
28. **Why is a replica read-only?** To prevent split-brain-style divergence: if a replica accepted independent writes, its keyspace would diverge from the primary's, and there's no conflict-resolution mechanism here to reconcile that. Writes from ordinary client connections are rejected with `READONLY`; writes arriving over the replica's own master link (internally, `conn is None`) are exempt, since those *are* the replicated stream.
29. **CAP-theorem framing for this design?** Under a network partition between primary and replica, MiniRedis chooses availability over consistency on the replica side: a partitioned replica keeps serving (possibly stale) reads rather than refusing them, and the primary keeps accepting writes rather than blocking on replica acknowledgment (replication is asynchronous, not synchronous — there's no `WAIT`-style quorum). The trade-off: a promoted replica after a primary failure could be missing the last few unacknowledged writes. That's an explicit, documented limitation, not an oversight.
30. **Why asynchronous replication instead of synchronous?** Synchronous replication (wait for a replica ACK before acknowledging the client's write) trades write latency and primary availability for stronger durability guarantees. Given this project's scope (single optional replica, no quorum/failover), the added complexity wasn't justified — it's called out as a documented future improvement, not implemented.

## Performance and scaling

31. **What are the realistic bottlenecks?** Python-level command parsing/allocation overhead per request, the storage lock's critical sections (short, but still serialize concurrent writers to the *same* key), `EXEC`'s exclusive gate window, `KEYS`'s O(n) pattern scan, and fsync latency under the `always` AOF policy. Run `benchmarks/suite.py` to get live numbers for your machine rather than trusting a claimed figure.
32. **Why report p50/p95/p99 instead of just an average?** Average latency hides tail behavior — a few slow requests (GC pause, a lock held slightly longer, a large pipelined batch) can be invisible in a mean but dominate real user experience. p95/p99 show what your *worst* typical requests look like, which is usually what actually matters for SLAs.
33. **How is this tested for correctness under concurrency, not just single-threaded logic?** Real `asyncio.gather`-driven concurrent clients (not sequential mocked calls) for racing GET/SET, TTL expiry under load, 40+ concurrent MULTI/EXEC transactions checked against a shared counter, and full two-process-equivalent primary/replica pairs talking over real TCP sockets on ephemeral ports.
34. **How would you scale this further?** (Explicitly *not* implemented here, to keep the core defensible — see the README's "Future Improvements" section.) Consistent-hash sharding across multiple primaries with a routing layer, Raft/Paxos-based automatic failover and leader election instead of manual `REPLICAOF NO ONE`, synchronous replication with a quorum for stronger durability, and eventually multi-region topologies. Each of those is a materially larger distributed-systems problem than anything in this codebase, which is exactly why they're future work rather than half-implemented here.
